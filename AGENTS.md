# AGENTS.md

Guidance for AI coding agents (and humans) working in this repository.

## What this app is

**Dientempo** ("diente" + "tiempo") is a native iOS SwiftUI app that helps people learn
Spanish number pronunciation while brushing their teeth. It counts 0 -> 200 out loud in
Spanish, timed to a ~2-minute brushing session, with `AVSpeechSynthesizer`.

- Bundle ID: `com.bystruev.dientempo`
- Deployment target: **iOS 16.0** -- keep this in mind before using newer SwiftUI/Swift APIs
  (e.g. the two-parameter `.onChange(of:) { old, new in }` needs iOS 17+; use the
  single-parameter `.onChange(of:) { new in }` form instead).
- Swift language version: 5.0 (not Swift 6 strict concurrency, but recent Xcode toolchains
  still warn on some actor-isolation mismatches -- see `PurchaseManager.swift` for the
  `nonisolated` + `Task { @MainActor in ... }` pattern used to keep StoreKit's
  non-actor-isolated delegate protocols clean).
- Development team: `8J39KF9DMS`.

**When starting a new feature or continuing an in-progress one:** read `STATUS.md` first (it
tells you what's actually done), then the corresponding `PLAN.md` section (it tells you the
intended design and any corrections already made to it). Don't re-derive the plan from
scratch by reading only the code -- the `## Log` in `STATUS.md` often records *why* the code
looks the way it does (e.g. a bug found in an early draft, a compiler limitation, a simulator
quirk hit during testing) which isn't otherwise visible.

## Build, test, and run

This project has no Swift Package Manager dependencies and no CocoaPods/Carthage -- it's a
plain `.xcodeproj` with explicit `PBXFileReference`s (not Xcode 16's synchronized folder
groups), so **new files must be registered in `project.pbxproj` by hand** (PBXBuildFile,
PBXFileReference, PBXGroup, and the relevant PBXSourcesBuildPhase entries) if you're not using
Xcode's GUI to add them. See the git history around the `PremiumManager`/`PurchaseManager`
addition for a worked example of doing this via a small Python script against the pbxproj
text format.

```bash
# List schemes/targets
xcodebuild -list -project Dientempo.xcodeproj

# Build for the simulator
xcodebuild build -project Dientempo.xcodeproj -scheme Dientempo \
  -destination 'platform=iOS Simulator,name=iPhone 17e'

# Run all tests
xcodebuild test -project Dientempo.xcodeproj -scheme Dientempo \
  -destination 'platform=iOS Simulator,name=iPhone 17e' -only-testing:DientempoTests

# Check which simulators are available if "iPhone 17e" doesn't exist on this machine
xcrun simctl list devices available
```

### Manual UI smoke-testing in the simulator

Useful, but has a gotcha: the simulator's `cfprefsd` daemon caches `UserDefaults`/`.plist`
state in memory. If you edit an app's preferences plist on disk directly (e.g. to simulate
"already ran today" for `PremiumManager`) while the app isn't running, the *daemon's* cached
copy can still win and clobber your edit the next time the app writes anything. If a manual
plist edit doesn't seem to take effect, restart the daemon inside the simulator before
relaunching the app:

```bash
xcrun simctl spawn <device-id> launchctl kickstart -k user/foreground/com.apple.cfprefsd.xpc.daemon
```

Find an app's sandboxed container (where its preferences plist actually lives) with:

```bash
xcrun simctl get_app_container <device-id> com.bystruev.dientempo data
```

## MCP tools available in this environment

Two local MCP servers are configured for this project:

- **`filesystem`** (`@modelcontextprotocol/server-filesystem`), scoped to
  `~/Desktop` and `~/Downloads` -- use for reading/writing/listing files under those roots.
  Note: this server has occasionally been flaky for large single writes (timed out on a ~200
  line file write during development); if a write call hangs, retry via the `shell` server's
  heredoc pattern (`cat > path << 'EOF' ... EOF`) instead of retrying the filesystem write.
- **`shell`** (`mcp-shell`) -- arbitrary shell command execution. Used for all `xcodebuild`/
  `xcrun simctl` invocations, git, and as a fallback for file writes when `filesystem` is slow
  or unresponsive.

Prefer `filesystem` for straightforward reads and small edits, and `shell` for anything
involving Xcode tooling, git, the simulator, or larger file writes.

## Conventions worth knowing

- **`ToothCountingViewModel` is `@MainActor` and drives all UI-affecting state.** If you add a
  new way to start a counting session, route it through `startCounting(from:)` (or make sure
  it eventually calls it) rather than duplicating start logic -- `onSessionWillStart` and the
  free-tier daily-limit recording depend on that being the single choke point.
- **`PremiumManager.canRun` and `timeRemaining()` must stay anchored to the same clock
  semantics** (currently: calendar midnight, via `Calendar.current`). If you change one,
  change the other, or the lock screen's countdown will disagree with when the app actually
  unlocks.
- **System frameworks (`AVFoundation`, `Speech`, `StoreKit`, etc.) auto-link** in this project
  without needing an explicit `PBXFrameworksBuildPhase` entry -- only `Foundation.framework`
  is listed explicitly, and that's a leftover default, not a requirement. Don't add framework
  entries speculatively; if `import Foo` alone doesn't link, that's a real signal to
  investigate, not the default expectation.
- **`SpeechCommandCenter.swift` is dead code** (voice-command recognition, removed from the UI
  in v1.4 per `test-notes.txt` -- "Removed speech recognition (no microphone permission, no
  vibration)"). It's still present in the target. Don't build on top of it without first
  confirming with the repo owner whether it should be revived or deleted.
